# Setting Up Owlbear Rodeo for Legend in the Mist

Legend in the Mist (LitM) runs on the Mist Engine (the same lineage as *City of Mist*/*Otherscape*): freeform Attributi (tags), leveled Stati (statuses), Temi (theme cards with Miglioria/Avanzamento/Abbandono tracks), and a 2d6 + Potere resolution against 10+/7-9/6- thresholds. There is no dedicated LitM (or Mist Engine) extension on the Owlbear Rodeo store, so this guide combines system-agnostic extensions for most mechanics, plus a **custom-built extension for the Hero sheet itself** (see below), since nothing off-the-shelf could represent Temi as real cards.

## Update: custom "Mist Engine — Hero Sheet" extension

After testing Dashboard Maker (too spreadsheet-like — plain draggable text boxes, no card visuals) and external options (Google Sheets can't be embedded live in Owlbear; Roll20's official LitM sheet could in principle be popped into Owlbear via the "Sheet from Beyond" extension, but only at the cost of running a whole second VTT + a paid Roll20 tier just to host it), we built a real custom Owlbear extension instead: a from-scratch web app using the official Owlbear SDK, styled as an actual parchment-and-card UI rather than a form.

The extension was originally built LitM-specific ("Carta Eroe"), then generalized at the user's request into a **Mist Engine** sheet that works across any game on this engine (City of Mist, Otherscape, Legend in the Mist, homebrew hacks), since the user runs multiple different settings on the same engine and didn't want a separate branded sheet per game. Key differences from the LitM-specific build:

- **Language:** defaults to English, with a one-click toggle (top-right of the panel) to switch to Italian at any time; the choice is remembered per browser. All UI chrome is bilingual via a `LABELS` dictionary in `app.js` — easy to extend with another language later.
- **Theme category & color — GM-configured campaign-wide (see below).**
- **Theme tracks:** every Theme has exactly 3 tracks (see the "UI rework" section below for how this landed — it started freeform, then was fixed to match the core book).
- **Generic field names:** "Quintessenze" → originally "Resource Pool" (Riserva), later removed entirely (see the second UI polish pass below); "Missione"/"Domanda del Tema" → "Quest" (renamed again in the UI rework below).

### GM-only Settings tab

The user pushed back on the first generalized version: it gave every player a free 5-color swatch picker per Theme with no shared meaning across the table. What they actually wanted was a GM-configured, campaign-wide list of Theme categories (e.g. LitM's Origin/Adventure/Greatness), so every Hero sheet at the table stays color-consistent — the color scheme is a campaign setting, not a per-player whim.

Implementation: a "Settings" tab appears in the topbar, but **only when the viewer's Owlbear role is GM** (`OBR.player.getRole() === "GM"`; always shown in standalone/local-preview mode since there's no room/role concept there). It lets the GM add/rename/recolor/remove Theme categories (label + one of 5 accent colors), pre-seeded with Origin/Adventure/Greatness by default. Stored once for the whole room via `OBR.room.getMetadata()/setMetadata()` under the key `com.mistengine.hero-sheet/campaign`, synced live via `OBR.room.onMetadataChange()`. As of the second UI polish pass below, this same campaign object also holds the GM's independent Tag-color/Status-color choices.

On each Theme's front, the category picker is a compact `<select>` dropdown (colored pill showing just the current category; the others stay hidden until clicked).

**Important nuance flagged to the user:** Owlbear has no real per-role write-permission system on room metadata — any connected client can technically call `room.setMetadata()`. GM-only tabs/controls in this extension are a UI-level courtesy (checking the role before rendering), not a hard security boundary — but that's how every Owlbear extension with GM-only features works, since there's no platform-level enforcement to lean on, and it's a non-issue for a table where everyone is already someone the GM invited.

## Major rearchitecture: GM-managed Roster + shared Compagnia card

This superseded the previous "each player gets their own Hero automatically, Party tab shows everyone read-only, GM can expand any Hero read-only" model entirely. Two problems drove it, both raised directly by the user with screenshots of the official LitM character sheet:

1. **"Compagnia" was modeled wrong.** The user pointed out that in the official rules, Compagnia isn't a party-roster summary — it's a specific card, the **Company Theme** ("Carta Tema di Compagnia"), structured exactly like a personal Hero Theme (3 Power tags, 1 Weakness tag, a Mission, three Abbandono/Miglioria/Avanzamento-style tracks, Special Upgrades) but shared by the whole party. Confirmed straight from the rulebook PDF in this project: the Company Theme "può essere migliorato, sostituito o evoluto allo stesso modo dei Temi degli Eroi" (same 3-track mechanic as personal Themes), and its Power tags "sono a uso singolo. Vengono barrati quando vengono attivati e non possono essere bruciati per ottenere Potere" (crossed off when used, not burned for a Potere bonus like personal tags — different fiction, same click-to-toggle interaction). The official card bundle is literally "Carta Eroe + Carta Eroe + Carta Tema di Compagnia."
2. **GM needed real edit access, not just read-only.** The user wants to add Statuses etc. directly to a player's sheet as GM. Owlbear's SDK doesn't allow this under the old model — a client can only write its *own* `OBR.player.metadata`, never another connected player's. The only bucket every client can write is room metadata, so all character data had to move there.

This was planned with the user via Plan Mode (research into the official PDF, three clarifying questions, written plan, explicit approval) before implementation. Key decisions:

- **Company Theme**: GM has full edit rights (Mission, tag text, add/remove tags, tracks, Special Upgrades). Players can only toggle a tag's crossed/used state — everything else read-only for them. Any Hero can activate a Power tag; the GM can activate the Weakness tag against any Hero.
- **Character visibility/assignment**: a 3-way per-character toggle — **GM only** (hidden from all players — NPCs, secrets, WIP sheets), **Everyone** (every connected player can view *and edit* it — covers one-shot pregens anyone can grab), or **a specific connected player** (assigned owner; only the GM and that player can view/edit).
- **Assignment persistence**: `OBR.player.id` is stable for the same player rejoining the same room (it's a synchronous getter in the SDK backed by the message bus's `userId`, confirmed by reading the bundled SDK source), distinct from a per-connection id that changes every connection — so an assignment survives normal reconnects. Not guaranteed across a browser/device switch (undocumented for anonymous/guest identities); the GM just re-assigns if that happens.
- **Deferred to a possible follow-up** (real mechanics, confirmed in the rulebook, scoped out to keep this shippable): the "Relazioni della Compagnia" table (per-companion relationship tags on each Hero Card), and the "Compimenti" (Fulfillments) tracker (insufficient rule detail surfaced to implement confidently).
- **Removed**: the old Party tab (roster summary + GM read-only full-sheet expand) — fully superseded by the new Compagnia tab (the actual Company Theme) and the Roster tab (full GM edit access per character).
- No data migration was needed — nothing had been deployed to a real Owlbear room yet.

### Data model

All character/campaign data lives in `OBR.room` metadata (not per-player metadata), split into independently-writable keys so concurrent edits by different people never clobber each other:

- `com.mistengine.hero-sheet/campaign` → GM's Theme categories, plus (as of the second UI polish pass) `tagColor`/`statusColor`.
- `com.mistengine.hero-sheet/company` → the one shared Company Theme card (power/weakness tags, 3 tracks, mission, special upgrades).
- `com.mistengine.hero-sheet/roster` → a lightweight index only: `{id, access: "gm"|"everyone"|"assigned", ownerId}` per character (no sheet contents, so renaming/reassigning one character never touches another's data).
- `com.mistengine.hero-sheet/character/<id>` → one key per character holding its full sheet (Background, Themes, Backpack, Active Tags, Statuses, Notes — Resource Pool was removed, see below) — independently writable, so the GM editing one character in Roster and a player editing their own sheet at the same time don't race.

### Tabs

- **Hero** (everyone; originally labeled "My Sheet", renamed in the UI rework below) — resolves which characters this player can access (`access === "everyone"` or assigned to them). Zero → "ask your GM" message. One → shown directly. Two+ (e.g. one-shot pregens) → a small picker to switch between them.
- **Compagnia** (everyone) — the shared Company Theme card described above; GM full edit, players can only cross tags.
- **Roster** (GM only) — "+ Add Character", a list of every character with a name field, the 3-way access `<select>` (GM only / Everyone / one option per currently-connected player), remove button, and an expand toggle (accordion — one open at a time) that renders the exact same full character-sheet editor used on the Hero tab, inline, so the GM can fully edit any character's Themes/tags/tracks/Backpack/Active Tags/Notes directly.
- **Settings** (GM only) — Theme categories, plus the Tag-color/Status-color pickers.

Implementation note: the entire sheet-rendering codebase (Theme flip cards, tag burn/cross, track dots, category dropdown, Backpack, Active Tags, Notes) was refactored to take a `(character, save)` pair instead of closing over a single global Hero, so the exact same tested UI renders "my own sheet," "the GM editing any Roster character," and (via a generalized read-only mode) the shared Company Theme, with no duplicated code.

**Same permissions caveat as the Settings tab**: hiding the Roster tab from non-GM players, and hiding a "GM only" or someone-else's-assigned character from a player's Hero tab, is enforced by this extension's own UI, not by Owlbear itself — there's no platform-level multiplayer permission system to lean on. Non-issue for a table where everyone is already someone the GM invited.

## Real deployment log: GitHub Pages, and two real bugs found along the way

The user created a public GitHub repo named `owlbear-mist-sheet` (account `nebula-rum` — renamed from `apudnebula` after initial deployment; if any older notes or links still say `apudnebula`, treat `nebula-rum` as current) and deployed via GitHub Pages (Settings → Pages → Deploy from branch → `main` / root). Two separate real issues surfaced during first install — both now fixed in the source and documented here so they don't recur in a future rebuild:

**1. Manifest paths were wrong for a GitHub Pages *project* site.** `owlbear-extension.json`'s `action.icon`/`action.popover` originally used bare relative paths (`"icon.svg"`, `"index.html"`, no leading slash). Confirmed against Owlbear's own tutorial docs (`docs.owlbear.rodeo/extensions/tutorial-hello-world/create-your-manifest/`, which shows `"icon": "/icon.svg"`, `"popover": "/"`): these paths resolve as **absolute, domain-root paths**, not relative to the manifest's own folder — and with no leading slash at all, Owlbear appears to concatenate origin + path with no separator, producing a malformed host (`<user>.github.ioindex.html`, a real "Server Not Found" the user hit). Separately, even with a leading slash, a GitHub Pages *project* repo (`username.github.io/repo-name/`) serves under a subpath, not the domain root, so a bare `/icon.svg` would resolve to the wrong place. This bit the user a *second* time after the `nebula-rum` account rename (a freshly re-uploaded manifest had reverted to the generic un-prefixed paths, producing the exact same "There isn't a GitHub Pages site here" 404). **Fix, now the shipped default:** `owlbear-extension.json` ships with the repo-specific paths baked in — `"icon": "/owlbear-mist-sheet/icon.svg"`, `"popover": "/owlbear-mist-sheet/index.html"` — so this repo's manifest works out of the box; the README's Contributing section explains that a differently-named fork needs those two paths updated to match (and flips them back to bare `/icon.svg`/`/index.html` for Netlify, which serves from the domain root).

**2. Real code bug: wrong Owlbear SDK method name.** After the manifest loaded and the icon appeared, the panel got stuck forever on "Loading…". The browser console (which the user retrieved for us) showed: `Uncaught (in promise) TypeError: (intermediate value).room.onChange is not a function`. Root cause: `app.js`'s `boot()` called `OBR.room.onChange(...)`, but the Room API has no such method — the real one is `OBR.room.onMetadataChange(...)`. Confirmed two ways: Owlbear's docs (`docs.owlbear.rodeo/extensions/apis/room/`) list `onMetadataChange` as the only change-subscription method on `OBR.room`, and reading the bundled SDK's own source (`obr-sdk.bundle.js`) directly — `RoomApi` (the class backing `OBR.room`) defines `getMetadata`, `setMetadata`, `onMetadataChange`, `onPermissionsChange`, and a synchronous `get id()`, but no generic `onChange`; the `onChange` name only exists on unrelated classes like `ThemeApi`, `PlayerApi`, `PartyApi`. **Fix applied:** changed to `OBR.room.onMetadataChange(...)`. This was a genuine authoring bug (most likely copied the `onChange` pattern used correctly elsewhere for `OBR.player`/`OBR.party`, which really do have `onChange`, without checking that `OBR.room` names its equivalent differently), not a deployment issue. While investigating, also re-verified every other `OBR.*` call directly against the bundled SDK source; all others were already correct. Also re-confirmed the bundled `obr-sdk.bundle.js` is byte-for-byte identical to a fresh build of the latest published `@owlbear-rodeo/sdk` (3.1.0) — ruled out as a stale-SDK problem before finding the real bug.

**Netlify gotcha (still applies, from earlier testing, unrelated to the two bugs above):** a file literally named `manifest.json` gets 401 Unauthorized on Netlify Drop (collides with their own web-app-manifest handling). Fix already applied and carried through every build: the manifest is named `owlbear-extension.json` instead.

**GitHub Pages transient deploy failures (infra, not our bug):** the user hit a `deploy-pages` GitHub Actions run that failed with a `500` from GitHub's own `createPagesDeployment` API (the action's own error text even suggested checking githubstatus.com for an outage). Checked githubstatus.com at the time — Pages and Actions both showed "All Systems Operational," so this was a brief transient blip, not a sustained incident. Resolution: just re-run the workflow (Actions tab → the failed run → Re-run jobs); no code or manifest change was involved.

Both fixes got the panel loading successfully in the user's live room (icon showing, sheet rendering, past "Loading…"). Live deployment: `https://nebula-rum.github.io/owlbear-mist-sheet/`.

## UI rework: fonts, a larger view, simpler tags, fixed 3-track backs, a Background box

Once the extension was actually working live, the user came back with a detailed list of UI/UX changes based on using it for real and comparing against the official card layout. All implemented in one pass:

- **Per-player font-size scaling.** Two new buttons next to the language toggle, **A−** / **A+**, step `document.documentElement.style.fontSize` through `[13,15,17,19,21]` px (the CSS is almost entirely `em`-based off the root, so this cascades cleanly). Persisted per-browser in `localStorage`, independent of everyone else at the table — this was explicitly requested as a personal-preference toggle rather than a single global size change.
- **A larger "expanded" view.** An expand-icon button (SVG, next to the font buttons) opens the *same* `index.html` a second time at `?view=expanded`, either via `OBR.modal.open({id, url, width:1180, height:820})` inside Owlbear, or a plain `window.open(...)` popup outside it (local preview). The button becomes a collapse icon inside that view and calls `OBR.modal.close(id)` / `window.close()`. `.themes-grid` was switched from a fixed vertical stack (`display:flex; flex-direction:column`) to `display:grid; grid-template-columns: repeat(auto-fit, minmax(230px, 1fr))` — at the narrow ~440px popover width that's still a single column, but at 1180px it naturally lays out up to 4 Theme cards side by side, exactly the "consult all 4 Themes at once" the user asked for, with no separate "wide mode" flag needed for the grid itself.
  - **A second real Owlbear SDK footgun found and avoided here, proactively:** the SDK's `normalizeUrl()` (used by `OBR.modal.open`) does the *exact same* unsafe `origin + url` string concatenation (no separator) as the manifest-path bug above, if `url` doesn't start with `"http"`. Passing a relative path like `"index.html?view=expanded"` would have reproduced the "Server Not Found" bug inside the modal too. Avoided by building the URL from `window.location.origin + window.location.pathname + "?view=expanded"` — i.e. deriving an already-absolute URL from wherever this page actually is currently running, which works regardless of GitHub Pages subpath / Netlify root / custom domain, and sidesteps `normalizeUrl`'s footgun entirely since it left the string untouched once it starts with `"http"`.
- **Quest field renamed and moved.** "Theme Question" / "Domanda del Tema" → literally **"Quest"** in both English and Italian (the user's explicit instruction — not translated), and moved from the top of the Theme's front face to after the Weakness tag (was: title → type → Quest → Power → Weakness; now: title → type → Power → Weakness → Quest).
- **Tag section headers simplified.** "⚔ Power Tags (click the icon to burn)" / "🩹 Weakness Tag" → plain **"Power Tags"** / **"Weakness Tag"**, no icon prefix, no parenthetical instructions. The old "+ tag" / "+ weakness" button below the tag list is gone; a small round "+" now sits inline in the header, to the right of the title (`renderTagList` now renders its own header+button instead of the caller prepending a separate label).
- **New icons, not unicode glyphs.** The card-flip button's "↻" was reported illegible in-client — replaced with a hand-built inline SVG (a clean two-arrow loop icon) via a small `svgIcon()` helper, guaranteed to render identically everywhere instead of depending on a font's glyph coverage. Same approach for the expand/collapse buttons. The Weakness tag's unburned-state icon (previously the 🩹 emoji) is now an inline SVG double-chevron-down, matching the actual Legend in the Mist rulebook's Debolezza icon (the user attached the official card's icon as reference) — shown only on the tag pill itself, not as a title-prefix.
- **Top row consolidated.** The flip button used to sit alone on its own row above the category picker, wasting vertical space; it's now merged into the same row as the category picker (`justify-content:space-between`), alongside the Theme's delete button (moved up from a footer at the bottom of the card, and relabeled from "Remove Theme" to just **"Delete"** — later changed to an icon-only trash button in the second UI polish pass below).
- **Special Track removed entirely.** The character-level optional 5-dot "Special Track (endgame/legendary arcs)" feature — a distinct thing from a Theme's own tracks — was dropped per explicit request: function, data fields (`specialTrackUnlocked`, `specialTrack`), and labels all removed.
- **"Click ↻ to flip the card…" hint text removed** from under the Themes section title, now redundant with the clearer flip icon.
- **New collapsible Background box**, right under the character name field: a toggle button (▸/▾ Background) reveals a free-form textarea for the player's own character story. New `character.background` field (default `""`), open/closed state is ephemeral per-browser (not synced), same pattern as the Roster's expand/collapse accordion.
- **Theme back locked to exactly 3 tracks**, matching the core book, instead of the earlier "freeform, add as many as you want" design. `defaultTheme()`/`defaultCompany()` now seed exactly 3 tracks with default labels **Abandon / Improve / Advance** (Abbandono / Miglioria / Avanzamento in Italian) — still freely renameable per track, just no button to add a 4th or remove one. Existing saved Themes/Company data with fewer than 3 tracks are padded up to 3 on load (`ensureThreeTracks()`), so no data is lost for anything already in play; nothing truncates data with more than 3.
- **Tab renamed.** "My Sheet" / "La Mia Scheda" → **"Hero"** / **"Eroe"**.

All of the above was verified via a full Playwright standalone pass (font-size persistence across reload, theme field order, header/inline-add-button structure, chevrons-down SVG present on weakness tags, Background box open/save, exactly-3-tracks with no add/remove UI on the back, and the expanded popup view actually opening at 1180px and laying out 3+ Theme cards horizontally) plus visual screenshots of the front, back, and expanded views — all matched expectations on the first pass, no follow-up fixes needed.

## Second UI polish pass: trash icons, wrapping titles, solid category colors, and the Active Tags rework

A further round of feedback after real table use, all implemented and verified via Playwright + screenshots:

- **Theme delete → trash icon.** The "Delete"/"Elimina" text button on each Theme card is now icon-only (a hand-built SVG trash can, `trashIcon()`), keeping the same tooltip text and the same `confirm()` dialog it already had.
- **Long Theme titles now wrap.** The title field was a plain `<input>`, which can't wrap and was clipping longer titles. Converted to the standard CSS-grid "replicated value" auto-grow trick: a `<textarea>` sits on top of a hidden `::after` pseudo-element that mirrors the same text (via a `data-replicated-value` attribute updated on input) — the grid row's height tracks the pseudo-element's wrapped content, so the textarea grows to fit without any JS height-measuring code. New helper: `renderThemeTitleField()`.
- **Confirm before deleting a Backpack item.** Theme delete already asked for confirmation; Backpack item delete now does too (`confirm(t("removeItemConfirm"))`), matching the pattern used everywhere else destructive actions happen.
- **Power tag icon → claw-scratch marks.** Replaced the "⚔" unicode glyph with a hand-built inline SVG of three diagonal claw-scratch lines (`clawIcon()`), matching the Legend in the Mist book's own Power-tag icon style (the previous chevrons-down icon for Weakness tags, from the prior UI rework, stays as-is).
- **Theme cards tinted by category color.** Each Theme's front/back face now gets a background tinted with its category's muted `--*-soft` color variable (the same tokens already used for tag pills etc.), instead of the same flat parchment gradient for every category — makes categories visually distinct at a glance, not just via the small pill/border. **First attempt used a gradient fade** (`linear-gradient` from the muted color into parchment); the user flagged that the fade read as unintentional/blurry in the preview and asked for a flat, solid color instead — changed to a plain solid `background: var(--amber-soft)` (etc., one rule per color) with no gradient.
- **Resource Pool removed entirely.** The user didn't know what it represented ("Riserva"/Quintessenze — not a concept they use) — function, call site, `character.resourcePool` field, labels, and CSS (`.quint-row`/`.quint-gems`) all removed.
- **Bug found and fixed while testing the above:** a Theme's assigned category could silently stop matching after the very next re-render, because `getCampaign()` minted a **brand-new set of random category IDs on every call** whenever the campaign hadn't been persisted yet (which was true for any room until the GM manually edited something in Settings). A theme created with `defaultTheme()`'s default category would immediately show "Choose a category…" instead, because the category picker's next `getCampaign()` call generated different IDs than the ones just assigned. This would have undermined the new muted-background feature (nothing would ever show a category color out of the box). **Fix:** `getCampaign()` now writes its first-ever default through to `roomMeta` (and schedules a save) the first time it's called with nothing persisted yet, so category IDs are stable from the moment a room is created, not just from the moment the GM opens Settings.

### Active Tags rework (mockup approved before building)

The old "Active Statuses" section had one item shape (name + an ever-incrementing `level` counter, click to raise/shift-click to lower) used for everything. The user wanted two distinct kinds of item under a renamed section, and — because this touches the data model — asked for a mockup to sign off on before real implementation. A standalone HTML mockup (not wired into the app) was built and screenshotted, showing both card shapes and the color-picker concept; the user approved it ("looks really nice") and it was then built for real:

- **Section renamed** "Active Statuses"/"Stati Attivi" → **"Active Tags"/"Tag Attivi"**, with two separate add buttons in the section header: **"+ Tag"** and **"+ Status"**.
- **Tag** (`character.tags`, new array): just `{id, text}` — a name and a delete button, no counter at all. Rendered as a pill (`renderActiveTagsSection`'s tag branch), styled with the CSS class `active-tag-chip`.
- **Status** (`character.statuses`, reshaped): now `{id, name, boxes: [bool×6]}` instead of `{id, name, level}` — six independently-toggleable numbered boxes (1–6) rendered as a small grid inside a `status-card`, each box its own on/off click target. This matches how the rules actually track a Status's tiers (not always crossed off strictly in order), unlike a Theme's track dots (which fill a contiguous prefix). - **Confirm before deleting**, on both Tag and Status items — same `confirm()` pattern as Theme/Backpack deletes.

Verified via Playwright: added 2 Tags + 2 Statuses, filled in names, toggled a Status's boxes non-sequentially (1, 2, 4 lit but not 3) to confirm independent toggling, confirmed the delete-confirmation dialog's cancel path leaves the item in place and its accept path removes it, and screenshotted the Settings tab showing both new color pickers — all matched the approved mockup.

### Real bug found in the field: the browser's native confirm() can be permanently silenced

Every delete button (Theme, Backpack item, Tag, Status, Roster character) used the browser's native `confirm()` — `if (!confirm(t("...Confirm"))) return;`. The user accidentally clicked Chrome's "Don't allow this page to create additional dialogs" checkbox on one of these prompts, which — as the browser is designed to do — permanently silences *all* future `confirm()`/`alert()` calls for that page load: `confirm()` then returns `false` instantly, with no dialog ever shown again. Since every delete handler was gated on `if (!confirm(...)) return`, this silently turned every delete button in the app into a dead button, with no error and no visible sign of what happened, until the page/panel was reloaded (the suppression isn't saved anywhere — it resets on reload, which was the immediate workaround given to the user).

**Real fix, not just a workaround:** stopped depending on the browser's native `confirm()` at all. Added `showConfirmDialog(message, onConfirm)` — a small in-app modal (dark overlay + parchment-styled box with Cancel/Delete buttons, dismissible by clicking outside or pressing Escape) rendered directly into the DOM via the existing `el()` helper, appended to `document.body`. All 5 call sites (Theme delete, Backpack item delete, Active Tag delete, Status delete, Roster character delete) were switched from `if (!confirm(...)) return; doThing();` to `showConfirmDialog(message, () => { doThing(); })`. New CSS: `.confirm-overlay`/`.confirm-box`/`.confirm-message`/`.confirm-actions`. New labels: `confirmCancel`/`confirmDelete` (EN "Cancel"/"Delete", IT "Annulla"/"Elimina"). Verified via Playwright with a `page.on("dialog", ...)` listener asserting the native dialog *never* fires, plus cancel-leaves-item-in-place and confirm-removes-item assertions — both passed, and a screenshot confirmed the visual matches the app's own parchment theme instead of a generic browser popup.

This class of bug (a delete/destructive action silently becoming permanently unusable due to a one-time browser setting, with zero error surfaced) is worth remembering as a general lesson for any future confirm-before-destructive-action UI in this app or others: prefer an in-app dialog over the browser's native one from the start.

## Third UI polish pass: relocated delete, trash-icon tags, minimal-by-default Theme cards

A further round of feedback aimed explicitly at reducing on-screen clutter — the user's framing was "reduce what is in the character sheet to the minimum so no distractions and get everything you need right away":

### The "double-click to delete" bug — root cause and fix

The user reported having to click a delete button, confirm, see nothing happen, then repeat the whole process a second time before the item actually disappeared. This traced to a real bug, not the earlier (already-fixed) native-`confirm()` silencing issue:

`bindCharacter(id)` / `bindCompany()` — the helpers that hand a render function `{character, save}` — built a **brand-new character/company object on every call** (`getCharacter()`/`getCompany()` always re-normalize into a fresh object) and immediately overwrote `roomMeta[key]` with it. That's fine on its own, but any full `renderApp()` re-render — triggered by `OBR.room.onMetadataChange` (which fires on *any* room metadata write, including echoes of the app's own saves), `OBR.player.onChange`, a font-size or language toggle — calls `bindCharacter()`/`bindCompany()` again and replaces `roomMeta[key]` with yet another new object.

If that happened while a delete-confirm dialog was open, the dialog's `onConfirm` closure still held a reference to the *old* (now orphaned) character object. Clicking "Delete" mutated that orphaned object; `save()` then persisted whatever the *current* `roomMeta[key]` was — the new, unmutated object — so the deletion was silently discarded. The next render re-read that same unmutated data, so the item reappeared as if nothing had happened. A second attempt worked because, by then, no re-render race was in flight, so the dialog's closure matched the live object.

Two-part fix in `app.js`:

1. **Stable object identity.** `bindCharacter()`/`bindCompany()` now reuse the *existing* `roomMeta[key]` object across re-renders instead of rebuilding it every call (only normalizing fresh when nothing valid is there yet, e.g. right after a genuine remote data change). As long as no real concurrent edit lands mid-dialog, a confirm dialog's captured reference now always matches what `save()` will actually persist.
2. **Defensive cleanup.** `showConfirmDialog()` now tracks the currently-open dialog and `renderApp()` closes it at the very start of every render pass (`closeConfirmDialog()`). Previously the overlay (appended to `document.body`, outside the re-rendered `#app` container) could survive a full re-render as a "ghost" dialog with stale data. Now, in the rare case a genuine concurrent change does land mid-dialog, the dialog visibly closes instead of silently no-op'ing — the user sees it disappear and knows to retry, rather than a delete that appears to do nothing. Also fixed while in there: the dialog's Escape-key listener was previously only ever removed on Escape itself, leaking one `document`-level `keydown` listener per dialog opened via Cancel/Delete/click-outside over a long session; it's now removed on every close path.

## Fifth pass: the delete bug's actual root cause, a missing confirm dialog, and the Theme card height fix redone

The user reported the delete bug was still happening intermittently ("works sometimes and sometimes not") after the fourth pass, and that "Show more"/"Show less" on the compact Theme card wasn't shrinking the card back down when collapsed — a lot of empty space stayed reserved. Both turned out to need a different fix than the fourth pass applied.

**The real delete-bug root cause.** The fourth pass's `bindCharacter()`/`bindCompany()` identity-stability fix only covered *some* of the ways a stale object reference could reach a confirm dialog's `onConfirm` closure. The actual, larger source of the bug was in `boot()`'s `OBR.room.onMetadataChange` handler:

```js
OBR.room.onMetadataChange((meta) => {
  const changed = JSON.stringify(meta) !== JSON.stringify(roomMeta);
  roomMeta = meta;              // <-- ran unconditionally, even when changed === false
  if (changed) renderApp();
});
```

OBR calls this handler with a **freshly deserialized object graph on every room-metadata write it sees — including no-op echoes of a save this very client just made, and writes to keys nobody touched.** `roomMeta = meta` ran unconditionally, so every single one of those echoes silently swapped every nested object (every character, the company, ...) for a new-but-content-identical instance — even though `renderApp()` was correctly skipped (via the `changed` check) and nothing visibly changed on screen. If a delete-confirm dialog happened to be open at that moment, its closure still pointed at the *old* character object; clicking "Delete" mutated that orphaned object, `save()` persisted the untouched replacement that `roomMeta[key]` now pointed to instead, and the delete silently did nothing — with no visual hint anything had happened, since no re-render occurred. This explains "sometimes works, sometimes doesn't": it depends purely on whether an unrelated metadata echo happened to land in the few hundred milliseconds between opening the dialog and clicking Delete, which is effectively random relative to the user's click timing. Fix: skip the `roomMeta = meta` reassignment entirely when `changed` is false, so object identities are only ever replaced when the content has genuinely changed.

**A real confirm-dialog gap, found while chasing the above.** While testing, found that deleting an individual Power or Weakness tag *from inside a Theme card* (the trash icon on the tag pill itself, not the Theme-level delete) skipped `showConfirmDialog` entirely and deleted on click with zero confirmation — a leftover gap from when tag deletes were switched from "✕" to the trash-icon style in an earlier pass; the wrapping in a confirm dialog never got added for that specific call site (it's shared code, `renderTagList()`, used by both personal Theme tags and the Company Theme's tags). Now wrapped in `showConfirmDialog(t("removeTagConfirm"), ...)` like every other delete in the app. New labels: `removeTagConfirm` (EN "Remove this tag?", IT "Rimuovere questo attributo?").

**The Theme card height fix, redone.** The fourth pass's fix (stacking both faces in one CSS Grid cell) solved the original "Show more content gets clipped by a fixed 430px" problem, but introduced a new one: since both faces contributed to the grid cell's height simultaneously, the card was always sized to *whichever face was taller* (front or back) — so collapsing "Show more" back down no longer shrank the card at all, it just left the space the taller face (usually the back, with 3 tracks + Special Upgrades) needed still reserved and empty. Replaced with a different technique: only the face **currently showing** is kept in normal document flow (`position: relative`, so it determines the container's height); the other face is taken out of flow (`position: absolute; inset: 0`) so it can't inflate the box. Which face is in-flow swaps with the `.flipped` class, alongside the existing `pointer-events` swap. Net effect: the front's own Show-more/Show-less state now directly and correctly controls the card's height while viewing the front (verified: collapsed 131px → expanded 239px → collapsed again back down to 131px, exactly), and flipping to the back sizes the card to the back's own natural height (388px, verified with `scrollHeight === clientHeight`, no clipping) — never the max of both.

Verified via Playwright (standalone backend): the collapse/expand/collapse height sequence above; flipping to the back and confirming its height and no overflow; flipping back to front confirms it returns to the same collapsed height; backpack delete, Theme tag delete (now confirms), and Company tag delete (now confirms) all show the dialog and correctly remove the item on confirm. As before, the `onMetadataChange` race itself can only be exercised on the real `obr` backend, not standalone — but the fix removes the actual mechanism that was causing it (the unconditional `roomMeta` swap on no-op echoes), rather than only patching one of its symptoms, so it should hold up now.

## Thirteenth pass: fixed the background vignette landing mid-page instead of framing the viewport

The user noticed an odd background color change near the bottom of the sheet that seemed to only belong on a footer, but visibly cut across Backpack and Notes instead.

Root cause: `html, body { height: 100%; background: radial-gradient(...top left...), radial-gradient(...bottom right...), var(--parchment); }` painted the same two-corner decorative vignette independently on both `html` and `body`. That handoff point — wherever the shorter, viewport-sized box happened to end — is where the "bottom right" dark shading landed, with a visible seam to the flatter, unshaded copy of the same gradient below it. On a character with a few Themes, a handful of Backpack items, and some tags, that seam happened to fall right around Backpack/Notes.

Fix: gave `html` a plain flat `background: var(--parchment)` (just a fallback base color, no gradients) and moved the two-corner vignette solely onto `body`, with `background-attachment: fixed`. That pins the gradient to the actual visible viewport rather than to a scroll-position-dependent box, so it's always a subtle vignette in the current window's corners — consistent regardless of how tall the sheet's content grows, no seam possible since there's only one copy of the gradient now.

Verified via Playwright: built a character with 4 Themes, 6 Backpack items, a Tag, and a Status (tall enough to require scrolling past one 820px screenful), scrolled to the bottom, and sampled background pixel colors along the right edge before/after the fix — before, color went from RGB(239,227,198) at the top down to (229,218,190) partway down, then jumped back up to a flat (242,230,201) for the rest of the page (the seam); after, it now shades smoothly and continuously all the way down with no jump. ## Fourteenth pass: Total Power tally — tick tags/statuses, auto-sum Potere, manual modifier

The user wanted the sheet to do the arithmetic Legend in the Mist asks a player to do by hand before every roll: add +1 per activated Power tag, -1 per activated Weakness tag, +3 instead of +1 for burning one Power tag, plus/minus the level of the single best helping and single worst hurting Status, and a Favored/Disfavored modifier — then show the running total live as a "Total Power" ("Potere Totale") readout next to the character name. The user asked directly whether this was worth building or better left to mental math, and proposed two possible interaction designs (an edit-icon mode to free up the tag's main click area, or a separate tickbox layered on top of the existing text editing) — a tickbox was recommended and chosen, since it needed no change to how tags are already edited.

Before designing anything, the exact formula was pulled from the rulebook PDF in this project rather than assumed from other Mist Engine games: the "Calcola il Potere dell'Azione" box (p.151) and "Ottenere più Potere" (p.158) confirm +1 per Power tag / **-1** (not +1) per Weakness tag, **+3** for burning one Power tag (replacing, not stacking with, its own +1 — and Weakness tags can never be burned), **±Level** of only the single best positive and single worst negative *active* Status (never a flat +1, never summed across every active Status), and **±3/±6** for Favored/Disfavored/Extremely-so, which the sheet can't infer on its own and so stays a manual box (doubling as the catch-all for GM-granted story tags and enemy Statuses).

Two decisions were confirmed with the user before building: Statuses use this rules-accurate best-positive/worst-negative math rather than a flat sum (so every Status now also carries a positive/negative flag, defaulting to positive for existing saved Statuses since there's no way to infer polarity from old data); and the running tally clears via a manual **Reset** button rather than automatically on tab switch, so a GM can build up a tally across several actions if they want.

What ticking actually means was scoped deliberately: it's scratch, per-viewer state for "the roll about to happen," never written to room metadata — the same pattern already used for things like which Theme cards are flipped. Only a tag's burned state and a Status's polarity/level are real, synced character data; the GM's own in-progress tally (editing a character via Roster) and a player's tally on their own Hero tab are independent, by design. A tick control (small square box, same visual as Backpack's existing "used" checkbox, just smaller) was added to: the Theme title (itself treated as a Power tag, matching its existing burn behavior), every Power/Weakness tag on a personal Theme, every Active Tag, and every Status (paired there with a small +/− polarity toggle). The shared Company Theme's tags deliberately do **not** get a tick control — they have different fiction (crossed off when used, never burned for Potere) and there's no per-party Potere tally to feed. Ticking a Status is mutually exclusive within its own polarity — ticking a second positive Status silently replaces the first tick, matching "only the single best counts" directly instead of leaving a player wondering why a second tick didn't change anything. Burning a Power tag automatically ticks it (so it immediately reads as the +3 it now is); un-burning it automatically un-ticks it, so it can't linger miscounted as a stray +1.

The Total Power chip, a narrow manual +/- number input, and a round Reset button were added to the header row, between the character name and the Background (book-icon) toggle. (This first version let the row wrap at narrow widths, dropping the cluster to its own line under the name on the compact 440px popover — later corrected to never wrap; see the Sixteenth pass below.)

**A real bug caught during verification, not just a design risk:** ticking or burning a tag inside a Theme card wasn't updating the visible Total Power number at all, even though the underlying tally was correct — Theme cards use a narrower re-render (`replaceThemeCard`, redrawing just that one card) that never touches the header sitting outside it, unlike Active Tags/Statuses, which already trigger a full tab re-render on every change. Fixed by having the Theme-card tick and burn handlers trigger that same full re-render instead. A second, smaller issue: the manual modifier's number input, at its intentionally narrow ~3-character width, let the browser's native up/down spinner arrows visually crowd out the digit itself — typing "-1" produced a box that only showed spinner arrows, no visible "-1". Fixed by hiding the native spin buttons via CSS (typing and the keyboard up/down arrows still work).

Verified via Playwright against hand-calculated totals through a full sequence: ticking 2 Power tags, a Weakness tag, and a Theme title (running total 1→2→3→2 as each was ticked); burning one Power tag (jumps to +3 instead of +1, confirmed against the formula); ticking an Active Tag (+1); ticking a positive Status at level 3 (+3) and a negative Status at level 2 (-2); setting the manual modifier to -1; confirming a second positive Status ticked afterward silently un-ticks the first (radio behavior) and the total updates to reflect only the new best; and confirming Reset zeroes the tally and the modifier while leaving the burned tag's permanent crossed-off state untouched. Screenshotted the header at both 1180px and 440px to confirm the new cluster never crowds or clips the name field.

## Eighteenth pass: Theme tag ticks back to the right, and a real cross-browser bug behind the Backpack burn's missing strikethrough

Two corrections right after the Seventeenth pass shipped.

**All Theme-card ticks (the title and its Power/Weakness tags) needed to be right-aligned after all.** The Seventeenth pass had moved a Theme's own tag ticks to the left to match the title pill's tick — but the user corrected course: both should sit on the right instead. The title pill's tick moved to the very end of the pill (after the title text; there's no delete button there to sit "before", but this keeps it consistent with every other tick in the app living at the right edge of its row). The Power/Weakness tag pills' ticks moved back to just before the delete button, undoing the Seventeenth pass's change and restoring the placement from two passes prior.

**The Backpack burn's missing strikethrough was a real cross-browser CSS limitation, not a simple oversight.** The user reported burning a Backpack item didn't show the same strikethrough a burned Power tag gets. Verified via Playwright: read back the Theme title pill's and tag pill's actual DOM order (tick now last in both); confirmed the Backpack row now renders its text through a `<textarea class="tag-text-input">` inside `.tag-text-wrap`, not a plain `<input>`; and confirmed `getComputedStyle` reports `text-decoration-line: line-through` directly on that textarea once burned, matching a burned tag.

## Twentieth pass: a roll button (2d6 + Total Power) and a persistent, shared roll-log corner panel

With the tick-and-tally UI settled, the user pointed out the one remaining manual step: after ticking everything and reading the Total Power chip, the player still has to roll actual dice some other way and add the number by hand. They asked for a small dice button that rolls 2d6, adds Total Power, and shows the result — landing in its own toggleable panel docked to a corner of the screen, visible to the whole table, keeping a history that survives everyone leaving and reopening Owlbear (not just the current session).

**Researched piggybacking on an existing dice extension first, and ruled it out.** Owlbear extensions can't call into each other directly; the only cross-extension mechanism is a generic room-wide broadcast pub/sub (`OBR.broadcast`). Cloned and read the official "Dice" extension's actual source directly (`git clone` + inspection, since a summarized fetch of the repo had initially — and wrongly — reported no relevant protocol at all): it has no public API for another extension to request a roll, only self-syncing. Two other, less broadly-installed community extensions (a SeamusFinlayson fork, and "Dice+" by Missing Link Dev) do expose their own bespoke roll-request broadcast channels, but they're two different, incompatible, unofficial protocols — depending on either would mean the button silently does nothing for anyone with a different (or no) dice extension installed. Decided with the user to skip third-party interop entirely and roll the 2d6 with `Math.random()` ourselves (the same RNG this codebase already uses for `uid()`) — zero dependency, always works, no risk of silent failure.

**Found the exact mechanism for "docked corner panel, visible to everyone" by reading the same official Dice extension's source.** A manifest can declare a `background_url` page that Owlbear loads once per connected player as soon as the room opens, independent of the toolbar-click popover. That page calls `OBR.popover.open()` anchored to a screen corner with its chrome hidden (`hidePaper`, `disableClickAway`) — exactly how Dice shows its own "other players' rolls" corner preview — and the same popover id can later be resized live via `OBR.popover.setWidth`/`setHeight` (confirmed directly in Dice's `PopoverTrays.tsx`), which gives a collapse/expand toggle for free with no new SDK concept.

Two decisions confirmed with the user via follow-up questions: broadcast every roll live to the whole table (not just the roller), and persist the roll history in room metadata (capped, not session-only) so it survives everyone leaving and reopening Owlbear — like a session log.

### Implementation

No `OBR.broadcast` needed at all — a roll is just one more capped array under its own room-metadata key (`com.mistengine.hero-sheet/rollLog`, up to 50 entries, oldest trimmed), following the exact same `ROOM_KEYS`/`scheduleRoomSave`/`OBR.room.onMetadataChange` pattern already used everywhere else in `app.js`. Every connected client — including the corner panel itself — already gets pushed live updates through that same listener.

- `rollDice(character)`: rolls 2d6, reads the existing `computeTotalPower(character)`, appends `{id, characterId, characterName, dice, power, total, timestamp}` to the log, saves. Deliberately doesn't touch `rollSelection`/`rollModifiers` — rolling and the manual Reset button stay independent actions, same as the Total Power tally's own design.
- A small dice-icon roll button sits in the header's Total Power cluster (`renderNameAndBackgroundSection`), so it appears on both the Hero tab and the GM's Roster inline editor for free.
- **The corner panel is this same app loaded a third way**, following the exact precedent of the existing `?view=expanded` modal: a new `?view=rolllog` flag skips the whole character-sheet UI and renders only a collapsed "🎲" pill that expands, on click, into a scrollable list of rolls (newest first) plus a Clear button. In real Owlbear, `background.html` opens this page automatically into a corner popover on `OBR.onReady`; the expand/collapse toggle resizes that same popover via `setWidth`/`setHeight`. Outside Owlbear (standalone/local-preview mode, where `OBR.popover` doesn't exist), the identical panel is instead embedded directly into the main page as a `position: fixed` corner overlay, so the feature stays fully testable without a real room.
- `owlbear-extension.json` gained `"background_url": "/owlbear-mist-sheet/background.html"` — same root-absolute-path convention (and same GitHub-Pages-subpath reasoning) as the existing `icon`/`popover` paths.

**Deploy note flagged to the user, same as every previous manifest change:** `background.html` and the updated `owlbear-extension.json` need to be pushed to the live GitHub repo for the roll-log panel to appear in a real Owlbear room — this can't be verified from local/standalone preview, since `OBR.popover`/`background_url` only exist inside an actual room.

Verified via Playwright in standalone mode: rolling produces a log entry whose `2d6 + Power = Total` math checks out; the panel starts collapsed and expands/collapses on click; rolling 54 times in a row caps the log at 50 entries; Clear empties it (behind the same in-app confirm dialog used everywhere else, not the browser's native `confirm()`); and a second page loaded at `?view=rolllog` against the same local room correctly picks up rolls made from the first page, confirming the underlying shared-state mechanism the real cross-client sync will ride on.

### Follow-up: log line reformatted to match the sheet, total colored by success band

Right after this shipped, the user asked for a formatting pass on each log line: the character's name in bold on its own line, then `2d6 (x+x) + Y = TOTAL` below it, with the Power number (`Y`) styled the same way it already is on the sheet (the Total Power chip's font/weight/color), and the roll's `TOTAL` bold and colored by outcome — green for a success, yellow for a mixed result, red for a failure, using the app's existing palette rather than introducing new colors.

Two more small requests right after: rolls should read like a chat log — newest at the bottom, not the top — and each character's name should render in its own color so a busy table's log is easy to scan at a glance, with the actual colors not mattering ("random" was fine).

### Follow-up: name colors made properly distinct, not just different

The hash-into-any-hue approach above technically gave every character *a* color, but nothing stopped two characters from landing on two close, hard-to-tell-apart hues (two different browns, say) — a real risk once a table has several players. The user asked for colors that are actually very different from each other, for tables of at least up to 6 players.

## Twenty-first pass: fixed the Settings tab's category list scattering across columns

The user reported visual bugs in the GM Settings tab: adding more Theme categories made rows spill outside the expected area, drifting left in a way that didn't make sense for what should be a simple vertical list.

Root cause, found by screenshotting the tab at the same 1180px width the default popover now opens at (since the Eighth/Ninth passes widened it): `renderSettingsTab()`'s category rows were wrapped in `.list-rows`, the exact class the Backpack section uses for its CSS multi-column masonry layout (`column-width: 230px`) — appropriate there, since Backpack items are short and meant to pack tightly side by side, wrong here. Once the container was wide enough to fit more than one 230px column, the browser split the category list across those columns using its own height-balancing algorithm — which doesn't just stack rows top-to-bottom, it slices straight through a row's flex children if that's where a column boundary falls. The result: a row's five color swatches and label would land in one column while its own ✕ remove button landed in the next column over, visually detached from the row it belonged to, and the rows themselves got reordered (top-to-bottom-then-across) instead of listed in a sane order. More categories meant more columns got used, making the scattering worse and more visible — exactly what the user described as "goes to the left."

Fix: gave Settings its own `.category-rows` class — a plain `flex-direction: column` stack, no multi-column layout at all — instead of reusing `.list-rows`. Also capped `.category-row` at `max-width: 420px` so rows read as a tidy list rather than stretching edge-to-edge on a wide screen, and added the missing `min-width: 0` to `.category-label-input` (the same flex-item-refuses-to-shrink bug fixed in several other places in this codebase already) so a long category name stays contained within its row instead of forcing the row wider than its container.

Verified via Playwright at both the wide (1180px) and narrow (440px, the popover's compact width) sizes: added up to 7 categories including one with a long name, confirmed the DOM order and the on-screen top-to-bottom order match (no more column-reordering), confirmed every row's ✕ button stays attached to its own row, and confirmed the long name stays inside its input instead of overflowing.

## Twenty-third pass: two roll-log bugs — Clear should be GM-only, and the empty/short panel floated in the wrong place

## Twenty-sixth pass: a dice-roll sound, heard by the whole table

The user asked for a sound to play whenever anyone rolls, audible to everyone in the room — not just the roller.

**No audio file shipped.** Rather than bundling an mp3/wav (adds a binary asset, plus a licensing question over wherever it came from), the "clack" is synthesized on the fly with the Web Audio API: 5 short bursts of filtered white noise, each with a quick decay envelope and a slightly different bandpass frequency/timing, reading as a handful of dice hitting a table rather than a single artificial beep. Zero dependencies, zero new files — keeps the extension a plain static site.

**Who hears it, and when.** The roller hears it immediately, played synchronously inside the roll button's own click handler — that's a real user gesture, so the browser's autoplay restrictions never apply to it. Every other connected client hears it through the same live room-metadata sync the roll log itself already relies on: `OBR.room.onMetadataChange` (in `boot()`) now also compares the roll log's last entry's id against the last one this client has already played a sound for (`lastAnnouncedRollId`), and plays the sound the moment that id changes. This distinguishes three cases that all fire the same `onMetadataChange` event: a genuinely new roll from someone else (plays), the round-trip echo of this client's own just-played roll (already marked announced at roll time, so it's skipped — no double-play for the roller), and the very first metadata sync right after the page loads (guarded by a `rollLogSoundReady` flag that only flips true once the existing roll log has been "pre-seeded" as already-announced, so reopening the extension with existing history never replays old rolls).

**Autoplay caveat, disclosed to the user directly:** browsers suspend a freshly created `AudioContext` until its page/frame has seen at least one user gesture. The roll-log corner popover (`?view=rolllog`, opened automatically by `background.html`) may never receive a click from a given player if they never touch it — so that player's very first roll of the session (someone else's, not their own) could play silently until they click anything in that popover (e.g. the collapsed pill), after which every subsequent roll plays normally for them. This is a real, disclosed browser limitation, not a bug to chase further; there's no way around it from inside the page.

**Personal mute toggle**, added alongside since a sound that's always on for the whole table with no way to turn it off individually seemed like an easy way to become annoying: a small speaker icon in the roll log's header (visible to everyone, not just the GM — this only affects the clicking player's own browser, stored in `localStorage`, same "everyone picks their own" pattern as the existing font-size control). Clicking it swaps to a muted-speaker icon and silences the sound for that viewer only; it has no effect on whether anyone else hears their own rolls.

Verified via Playwright: in standalone mode, confirmed rolling triggers the sound (spied on `AudioContext.createBufferSource` calls) both on the first and a subsequent roll. Using the fake-OBR-SDK route-interception technique (from the earlier Clear-button GM-gating pass) to simulate incoming room-metadata pushes without a live Owlbear room: confirmed a fresh remote roll plays the sound, an exact-echo push of the same roll log does not replay it, a second genuinely new remote roll plays again, and — after clicking the mute button — a third remote roll stays silent.

## Twenty-seventh pass: a real typing bug, plus two roll-log sizing tweaks

**The typing bug.** The user reported that a Settings text field (Theme category names, the new track names) would "deactivate" after a single keystroke, forcing a re-click to keep typing. Root cause: every keystroke schedules a debounced room-metadata save (`scheduleRoomSave`, 250ms), and — confirmed by an existing code comment from an earlier pass — Owlbear's own `OBR.room.onMetadataChange` fires back on the client that made the save too, not just other clients. That echo was landing ~250ms after the keystroke and triggering a full `renderApp()`, which rebuilds every DOM node in the app, including whichever input the player was still typing into — killing its focus. The existing guard against this (`JSON.stringify(meta) !== JSON.stringify(roomMeta)`, meant to skip re-rendering on a no-op echo) doesn't actually catch this case reliably: `JSON.stringify` is sensitive to object key order, and there's no guarantee a round-tripped object comes back with keys in the same order this client built them in — so a semantically-identical echo could still register as "changed" and force the teardown anyway.

Fixed with two layers, so the bug can't reoccur regardless of which exact mechanism was really firing it: (1) replaced the JSON.stringify comparison with a proper `deepEqual()` (structural, key-order-independent) so an actually-identical echo is correctly recognized as a no-op; and (2), as a second line of defense, `boot()`'s metadata listener now checks `document.activeElement` before rendering — if a text input or textarea currently has focus, the incoming data is still applied to `roomMeta` immediately (so nothing is lost), but the visual re-render is deferred until that field loses focus (a `focusout` listener flushes it then). This means even a *genuinely* different incoming change (e.g. another connected GM editing Settings at the same moment) can no longer interrupt whatever the player is actively typing — it just appears the instant they tab or click away.

Verified via the same fake-OBR-SDK technique used for earlier GM-gating tests, since this needed simulating a real metadata round-trip that the standalone/local-preview mode never triggers: typed into a category name field, pushed a same-content-but-differently-ordered-keys echo, and confirmed the exact same input element stayed focused with the typed text intact; then pushed a genuinely different remote change (an added category) while still focused and confirmed it stayed invisible until the field was blurred, at which point it appeared correctly.

**Roll-log sizing.** Two follow-up requests on the corner widget: the collapsed dice pill floating over the game table felt oversized, so it's now 32px (matching the scale of Owlbear's own round toolbar buttons) instead of 48px — the real popover box behind it is 40px so the pill's drop shadow still has a few px of room instead of being clipped at the window edge. And the expanded panel is now 322px wide, 15% more than the original 280px, at the user's request.

That second change surfaced an unrelated latent bug while verifying: `.roll-log-panel` was styled `width: 100%; max-width: 280px`, but its ancestors (`#app`, `.roll-log-widget`) are shrink-to-fit boxes with no definite width of their own inside the popover's flex layout — a percentage width against an indefinite containing block resolves to `auto` per the CSS spec, so the panel had actually been sized purely by its own content all along, and the `max-width` cap was never really being hit either way. Bumping 280→322 would have silently done nothing. Fixed by giving `.roll-log-panel` a plain explicit `width: 322px` instead, which renders reliably regardless of that ancestor chain — confirmed by measuring the panel's actual rendered bounding box at the popover's real pixel dimensions (a plain browser viewport doesn't reproduce this, since it isn't shrink-wrapped the same way the popover's flex layout is), not just eyeballing a screenshot.

## Twenty-eighth pass: "draggable" pill — research led somewhere different

The user asked to make the corner dice pill draggable, "like all other extension pills." Before building anything, cloned and read Owlbear's own SDK source (`owlbear-rodeo/sdk` on GitHub) and two dice extensions with the most comparable "floating tray" concept — the official `owlbear-rodeo/dice` and the actively-maintained `SeamusFinlayson/dice-extension` fork. Findings: `OBR.popover` only exposes `open`/`close`/`getWidth`/`setWidth`/`getHeight`/`setHeight` — no move/reposition method exists anywhere in the SDK, and the docs make no mention of drag at all. Neither dice extension implements true dragging either; the community fork's answer to "let players move it" is a plain left/right dock toggle persisted in `localStorage` (`getPopoverAlignment`/`setPopoverAlignment`), not continuous mouse-drag. The user's reference point turned out to be Owlbear's own toolbar-icon drag-to-reorder — a native, built-in behavior for icons living in Owlbear's toolbar strip, unrelated to (and unavailable to) a `background_url` popover like this roll-log widget.

Given all four screen corners were already reported as occupied by other extensions/native controls, a corner-picker toggle wouldn't have actually helped — so the ask became something more specific and much more tractable: nudge the pill up from the exact bottom-right corner so it clears Owlbear's own native scene/map-toggle button sitting right there.

**Fix, in `background.html`** (the only file that calls `OBR.popover.open()` — app.js only resizes the same popover afterward via `setWidth`/`setHeight`, it never repositions it): raised `marginThreshold` from `0` to `56`. This option is verbatim from Material-UI's Popover component (Owlbear's popover options match MUI's prop names exactly — `anchorOrigin`, `transformOrigin`, `disableClickAway`, `marginThreshold`), and unlike `anchorOrigin`/`transformOrigin` (which only pick a corner), MUI's `marginThreshold` keeps the popover at least that many px from *every* viewport edge — so raising it pushes our bottom-right-anchored pill up and slightly left instead of sitting flush in the corner, without needing genuine drag support at all. 56px is a reasonable guess at clearing a single native corner button, not a measured value — there's no way to check the real pixel layout of Owlbear's own UI from outside a live room, so this is flagged to the user as a starting point they may want to nudge up or down after seeing it deployed.

**Also fixed while in this file:** `background.html` had its own hardcoded `COLLAPSED_WIDTH`/`COLLAPSED_HEIGHT` (56×56) duplicating `ROLL_LOG_COLLAPSED_SIZE` from `app.js` — a leftover from the earlier pill-shrinking pass (twenty-seventh) that updated the `app.js` constant to 40×40 but missed this second copy, so the popover would have opened at the old 56×56 size on first load until the very first collapse/expand toggle corrected it. Updated to match.

Verified with a fake-OBR-SDK Playwright check spying on the exact arguments passed to `popover.open()`: confirmed `width`/`height` are now 40, and `marginThreshold` is 56. The actual on-screen clearance from Owlbear's native button can only be judged in a real room — flagged to the user as the one thing left to eyeball after deploying.

## Twenty-ninth pass: pill alignment fix, and a real cross-page mute bug

Two follow-ups after the last pass went live: the pill was now "a little off" from the right edge, and the mute button "doesn't really work."

**Alignment.** Root cause was the `marginThreshold: 56` fix from last pass — that option (confirmed against Owlbear's SDK types, and against how Material-UI's Popover, which Owlbear's popover options are lifted verbatim from, implements it) keeps a popover at least that many px from *every* viewport edge uniformly, not just the one it needed to clear. It was pushing the pill both up (wanted) and left (not wanted) by the same 56px, reading as "off" from the right. Reworked to be direction-specific instead: `marginThreshold` is back to `0` in `background.html` (flush on every edge, as far as the popover API itself is concerned), and the vertical-only gap is now created inside the widget's own page — `ROLL_LOG_COLLAPSED_SIZE`/`ROLL_LOG_EXPANDED_SIZE` in `app.js` each got a new `ROLL_LOG_BOTTOM_CLEARANCE` (56px) added to their *height* only, and `body.roll-log-view` in `style.css` got a matching `padding-bottom: 56px`. The popover box is simply made taller than the visible widget, and the page's own bottom padding is what actually holds the widget above the true edge — width, and therefore the right edge, is untouched, so the pill now sits flush right with clearance only from the bottom. Verified by measuring the widget's bounding box at the exact popover pixel dimensions for both the collapsed and expanded states: right edge flush with the viewport edge in both, bottom edge exactly 56px up from the viewport bottom in both.

**The mute bug — a real cross-page sync gap.** The mute button lives only on the roll-log corner popover's own page (`?view=rolllog`); the roll button a player actually clicks lives on the separate main sheet page, opened independently from the toolbar. These are two entirely different script instances, each reading `rollSoundMuted` from `localStorage` once at its own load time into its own module-level variable — clicking mute on the corner widget updated that widget's own copy (and `localStorage`) correctly, but the main sheet's already-loaded copy never found out, so a player's own rolls kept playing sound even after they'd muted. Fixed with a `window.addEventListener("storage", …)` listener: a `storage` event fires in every other same-origin page whenever one of them writes to `localStorage` (by design, it never fires in the page that made the write, which is why the existing same-page update still needed to stay as-is), so every open copy of the extension — the corner widget and the main sheet alike — now picks up a mute/unmute the instant it happens anywhere.

Verified with two Playwright pages sharing one browser context (one loaded as the corner widget, one as the main sheet, spying on `AudioContext` usage on the main-sheet page): rolling before muting produced sound as expected; muting via the corner widget's button and then rolling again from the main sheet produced no additional sound, confirming the fix actually closes the gap between the two pages rather than just working within a single one.

## Thirty-first pass: considered splitting into two extensions, landed on a simpler show/hide toggle

The user's next idea was to split the extension in two — the character sheet, and a standalone "Roll Log Viewer" — hoping for (1) the same free draggability other extension pills supposedly have, and (2) a viewer generic enough to also show rolls broadcast from other people's character-sheet extensions.

Both premises got checked against the Owlbear SDK source before building anything. **Draggability**: already confirmed in the prior pass that no shipped extension (official Dice, or a popular community fork) implements popover dragging — the SDK's own `PopoverApi.ts` exposes only `open/close/getWidth/setWidth/getHeight/setHeight`, no move/reposition method at all. Splitting the extension in two doesn't change what the SDK offers either half; it wasn't going to unlock dragging regardless of the architecture. **Cross-extension roll sharing**: read `RoomApi.ts` and `Metadata.ts` directly from the SDK source. `getMetadata()` returns the *entire* room metadata object and `setMetadata()` takes a `Partial<Metadata>` — `Metadata` itself is typed as a bare `Record<string, unknown>`, with no extension-id scoping anywhere in the request, and the `Permission` type (which does gate scene objects like maps/props/notes) has nothing for metadata either. So room metadata is already a single flat, shared key-value space today — any installed extension can already read or write our `com.mistengine.hero-sheet/rollLog` key, namespaced only by the prefix convention, whether or not the sheet and the viewer are one extension or two. Splitting wouldn't have been what made that possible; it already is.

With both stated motivations either false (dragging) or already true without a split (cross-extension reads), the actual remaining case for two extensions shrank to "a separately-installable product other GMs could adopt" — real, but a bigger lift (a second manifest/repo/install step, a documented public schema, both pieces needing to stay in lockstep) for a benefit the user hadn't actually asked for. Surfaced this via a clarifying question; the user's own follow-up cut straight to the actual itch: **just let a player turn the corner widget on or off from the sheet itself**, the same place font size and language already live — solving the real problem (the widget sits over Owlbear's native scene/map toggle, and not everyone wants it there) without a second extension.

**Implementation.** A new per-browser preference, `rollLogPanelHidden` (`localStorage` key `mist-hero-sheet-roll-log-hidden`, same "everyone picks their own" pattern as font scale and the roll-sound mute), toggled by a new dice icon button in the topbar (next to the expand-view button) — a plain dice glyph when the widget is showing, the same glyph with a diagonal slash when hidden. Real Owlbear lets *any* page belonging to an extension control a popover it already knows the id of — not only the page that originally opened it, already proven by the roll-log panel resizing its own popover from its own page via `setWidth`/`setHeight` — so the topbar button calls `OBR.popover.open()`/`close()` on the roll-log popover id directly, with no round trip through `background.html`. `background.html` (which normally opens that popover once, automatically, per connected player) now just checks the same `localStorage` flag once before its own initial `open()` call, so a player who hid the widget doesn't have it silently reappear on their next reconnect. ## Thirty-second pass: pushing the roll-log toggle live — a browser-automation deploy, since `git push` doesn't work from this environment

With the Thirty-first pass's code finished and locally verified (`node --check app.js`), pushing it to the live repo (`nebula-rum/owlbear-mist-sheet`) turned out to need a completely different mechanism than every previous deploy note in this doc assumed, worth recording since it'll apply to every future push too.

**`git push` from this sandboxed environment doesn't reach GitHub at all.** A normal `git remote add`/`git push` with a user-supplied personal access token embedded in the URL was rejected before it ever reached GitHub, by a mandatory local network proxy this environment routes all GitHub traffic through: `remote: access denied by the git proxy: <repo> is not in this session's authorized repository set, so the proxy will not inject a credential for it.` That proxy manages its own GitHub credentials and only authorizes pushes to repos explicitly connected through Anthropic's own "Connect GitHub" OAuth flow at claude.ai/code — a pasted token in the remote URL is simply ignored/overridden, not used. That flow is an account-level, one-time setup (not something fixable mid-session) and wasn't set up here, so it wasn't available this round. The exposed token the user pasted into chat while troubleshooting this was never actually used against GitHub (the push failed before leaving the sandbox) and was discarded from the local clone immediately; **the user should still revoke it**, since a token typed into a chat is best treated as burned regardless of whether it was ever exercised.

**Working alternative: drive an already-authenticated browser instead of using git at all.** The user connected a browser pane (already logged into GitHub as the repo owner) through the desktop bridge. Both files were pushed through GitHub's own web UI, automated end to end, with two different techniques depending on file size and risk:

- `background.html` (small, mostly comments) was typed directly into GitHub's file editor (which runs CodeMirror 6). This surfaced a real, repeatable automation bug worth flagging for any future file edited this way: typing multi-line text into CodeMirror 6 **duplicates every blank line** — each blank line in the source becomes two in the typed result (an auto-indent side effect), while single line breaks are unaffected. Since blank lines are purely cosmetic in HTML/JS, the fix was to collapse all blank lines out of the text before typing it, rather than trying to correct the count afterward — a follow-up attempt to fix a trailing-newline miscount with a few extra keystrokes actually corrupted real content once (deleted characters off the end of a closing tag), which is the reason "fix it before typing, never after" is the rule now, not "type then patch."
- `app.js` (~121,000 characters — much larger, and far more consequential to get wrong than a mostly-comment HTML file) used a different, more reliable path that avoids keystroke simulation entirely: the exact file content was assembled inside the browser page as a JavaScript string (built up in chunks, since a single automation call can only carry so much text at once), then turned into a real `File`/`Blob` object and fed directly into GitHub's upload-page file input via a `DataTransfer` — the same mechanism a real drag-and-drop populates — rather than typed character by character. No editor, no keystrokes, no auto-indent bug possible.

**Verification, both times: byte-exact via SHA-256, not a visual diff.** Every step compared a SHA-256 hash computed in the browser (`crypto.subtle.digest`) against a hash computed locally from the canonical source file, rather than trusting that a copy "looked right." One counterintuitive wrinkle worth remembering for next time: JavaScript strings count length in UTF-16 code units while Python/Node's usual string length counts Unicode codepoints, so a file containing any character outside the Basic Multilingual Plane (this file has exactly three — the 🔥 flame emoji used in a few burned-tag icons) will report a slightly different `.length` in a browser than in a local script, even when the actual bytes are 100% identical. This showed up mid-verification as an apparent 3-character discrepancy that briefly looked like a transcription error; comparing the full SHA-256 of the encoded bytes (which doesn't care how either language counts string length) confirmed the content was correct all along, and the live file's hash on GitHub was confirmed to match the local source exactly (`3768df54…afa9c9e8`) after the commit.

Both `background.html` (commit `c8dc7ad`) and `app.js` are now live on `main`, fetched back from `raw.githubusercontent.com` and hash-verified against the local source — this pass's roll-log-visibility topbar toggle is deployed, not just built. Worth the user's own final check in an actual Owlbear room (the same standing caveat as every popover/background_url-touching pass in this doc): confirm the new dice-toggle icon appears in the topbar next to the expand button, and that clicking it actually shows/hides the corner widget without needing a reconnect.

## Thirty-third pass: the topbar toggle now opens the log itself, not just the pill

Once the Thirty-second pass's show/hide toggle actually went live, the user's real-room feedback was that clicking it to "show" the widget wasn't doing what they meant: the corner popover reappeared, but only as its small collapsed dice pill — a second click on the pill was still needed to see the actual roll history. What the user wanted was for the topbar button's "activate" action to jump straight to the expanded chat-style log, since that's the thing they're actually pressing the button to see.

**Root cause.** The main sheet page (where the topbar toggle lives) and the roll-log popover page (`?view=rolllog`, where `rollLogExpanded` actually decides pill-vs-panel) are two separate script instances in real Owlbear — Owlbear loads each `OBR.popover.open()` URL as its own fresh page, with no shared JS state. `setRollLogPanelHidden(false)`'s only lever on the other page was `openRollLogPopover()`, which always opened `?view=rolllog` with no signal at all, so that fresh page instance always initialized `rollLogExpanded = false` — collapsed, every time, regardless of why it was being shown.

**Fix.** A new URL query flag, `open=expanded`, threaded through specifically for this one path: `openRollLogPopover()` now builds its URL as `?view=rolllog&open=expanded`, a new `rollLogOpensExpanded` constant reads that flag (`new URLSearchParams(window.location.search).get("open") === "expanded"`), and `rollLogExpanded`'s initial value became `isRollLogView && rollLogOpensExpanded` instead of a hardcoded `false`. Deliberately scoped to only the deliberate "activate" action: `background.html`'s own separate ambient auto-open-on-room-join call was left untouched (still no `open` param, still `COLLAPSED_WIDTH`/`COLLAPSED_HEIGHT`), so a fresh connection still starts as the small unobtrusive pill by default, exactly per the original Thirty-first-pass design intent — only clicking the topbar button jumps straight to the expanded log. Standalone/local-preview mode's embedded overlay (no popover URL to pass a flag through, since it's the same page instance) gets the same result by setting `rollLogExpanded = true` directly inside `setRollLogPanelHidden()`'s show branch.

**Verification**, three separate Playwright checks: (1) standalone mode, clicking the topbar toggle twice (hide, then show again) and confirming the widget comes back with a `.roll-log-panel` present and no `.roll-log-pill`; (2) a fake-OBR-SDK route recording `OBR.popover.open()`'s exact arguments, confirming the URL built for the "activate" action ends in `?view=rolllog&open=expanded` while `background.html`'s own ambient call still omits it; (3) loading `?view=rolllog&open=expanded` and plain `?view=rolllog` directly and confirming the former renders the expanded panel and the latter the collapsed pill. Pushed to `main` via the same browser-automation Blob/`DataTransfer` upload technique as the Thirty-second pass, and confirmed live via a byte-exact SHA-256 match between the local source and the file fetched back from `raw.githubusercontent.com` (`f8185f05…fd63f530d`).

## Thirty-fourth pass: lifting the corner widget clear of Owlbear's own map-toggle button

Real-room feedback again: the corner widget (both the collapsed pill and the expanded panel) was sitting slightly on top of Owlbear's own bottom-right scene/map-toggle control, despite the ROLL_LOG_BASE_BOTTOM_CLEARANCE (56px) tuned for exactly this back in the Twentieth pass. The user asked for the whole widget to sit roughly 5% of the screen height higher.

**Why a fixed pixel bump wasn't the right fix.** The existing 56px clearance is a flat number baked into the popover's box size and a matching CSS padding value — it was tuned once, on one screen, and a fixed px gap doesn't scale: on a taller/larger display the same 56px reads as barely anything, which is exactly the "still grazing the button" report. The user's own framing — a *percentage* of screen height — is the right unit for this, so the fix reads the real game-window height at runtime instead of hardcoding a bigger constant.

**Real-Owlbear path (`app.js` + `background.html`).** `OBR.viewport.getHeight()` (confirmed via the SDK bundle's own `ViewportApi` — a real round trip to the host page returning the visible game-table height in pixels) is read once at boot, multiplied by a new `ROLL_LOG_EXTRA_LIFT_FRACTION = 0.05`, and added on top of the existing `ROLL_LOG_BASE_BOTTOM_CLEARANCE`. `ROLL_LOG_COLLAPSED_SIZE`/`ROLL_LOG_EXPANDED_SIZE` (previously plain constant objects, computed once at module load before this async value could exist) became `rollLogCollapsedSize()`/`rollLogExpandedSize()` functions instead, called fresh wherever a popover is opened or resized (`openRollLogPopover()`, `setRollLogPopoverSize()`) so they always reflect the current lift. The roll-log widget's own page additionally overrides its CSS `padding-bottom` inline once the real value is known, since the flexbox-anchored layout (see the Twentieth pass's own notes in `style.css`) needs that padding to match the popover box's actual height for the widget to land in the right spot. `background.html` — a separate script instance that doesn't load the rest of `app.js` — duplicates the same formula (matching the file's existing pattern of duplicating small constants with a "must match app.js" comment) so its own ambient auto-open-on-room-join call sizes its popover box consistently with whatever the main sheet's script computes.

**Standalone/local-preview path (`style.css`).** No popover box to size here — the widget is a plain `position: fixed` overlay sharing the page with the character sheet — so the same "5% higher" reads as a one-line CSS change: `bottom: calc(14px + 5vh)`, using the browser's own real viewport height for free via `vh` units, no JS round trip needed.

**Verification.** Playwright, three checks: (1) standalone mode at a 900px-tall viewport, confirming the floating widget's gap from the bottom of the viewport is exactly 59px (14 + 5% of 900); (2) a fake-OBR-SDK route with `viewport.getHeight()` stubbed to return 900, confirming the roll-log page's own `body.roll-log-view` padding-bottom becomes 101px (56 + 45) and that collapsing the panel calls `setHeight` with 141 (40 + 56 + 45); (3) the same fake-SDK route pointed at `background.html` directly, confirming its own ambient `popover.open()` call requests the same 141px height independently. All three land on the same number from the same 900px input, confirming the three duplicated formulas (app.js's two call sites, background.html's own copy, and standalone's CSS) stay in lockstep. Pushed to `main` via the same browser-automation Blob/`DataTransfer` technique as prior passes, hash-verified against `raw.githubusercontent.com` after commit.

## Thirty-fifth pass: the map-toggle button still wasn't clickable — a pointer-events fix, separate from the lift

Right after the Thirty-fourth pass's 5%-lift went live, the user reported a second, related-but-distinct bug: even with the widget visually lifted clear of Owlbear's own bottom-right map/scene-toggle button, that button still wasn't properly selectable whenever the roll-log widget was present (open or minimized). Visually moving the widget's *content* out of the way didn't fix this, because the actual problem was never about where the pixels were drawn.

**Root cause.** The roll-log popover's DOM box (`body.roll-log-view`) is deliberately larger than the visible pill/panel — the extra margin is exactly the `ROLL_LOG_BASE_BOTTOM_CLEARANCE`/`ROLL_LOG_RIGHT_CLEARANCE`/lift padding introduced in earlier passes, so the widget can sit up and away from the popover's true bottom-right corner. But a browser hit-tests mouse clicks against an element's actual box, not just wherever it happens to have visible content — by default, every pixel inside that padded box, including the fully transparent margin around the pill, still captures clicks. Since that margin was deliberately sized and positioned to overlap Owlbear's own map-toggle button (that's the whole point of the clearance), clicks meant for the button underneath were landing on our own transparent padding instead and going nowhere — exactly what reads as "not properly selectable" from the player's side. The 5% lift from the previous pass made this worse in one sense: a *bigger* clearance box means a *bigger* invisible click-catching area.

**Fix, entirely in `style.css`, no `app.js`/`background.html` changes needed.** `html.roll-log-view`/`body.roll-log-view` now get `pointer-events: none`, turning the whole popover page click-through by default. `.roll-log-widget` (the actual visible pill/panel) gets `pointer-events: auto`, which — per how CSS `pointer-events` inheritance works — re-enables real hit-testing just for that one element and everything inside it, overriding the `none` it would otherwise inherit from its ancestors. Net effect: a click anywhere in the transparent margin now falls straight through to whatever Owlbear has underneath (the map-toggle button), while the pill/panel itself stays fully interactive for every existing control (collapse/expand, mute, clear, scrolling the log). This is purely a hit-testing change — nothing about layout, sizing, or the 5% lift from the previous pass was touched.

**Verification.** Playwright, using the same fake-OBR-SDK route-interception technique as prior passes (`viewport.getHeight` stubbed to 900, matching the Thirty-fourth pass's own check): loaded `?view=rolllog` at the popover's real collapsed pixel dimensions and confirmed via `getComputedStyle` that `body`'s `pointer-events` computes to `none` while `.roll-log-widget`'s computes to `auto`; then used `document.elementFromPoint()` at two coordinates — one in the empty top-left corner of the tiny popover viewport (clearly inside the padded margin, nowhere near the pill) and one at the pill's own actual center (measured via `getBoundingClientRect()`) — confirming the first resolves to nothing belonging to our page (click-through) while the second correctly resolves to the pill button itself (still clickable). Pushed to `main` alongside the Thirty-fourth pass's remaining un-deployed lift work in one commit, via the same browser-automation Blob/`DataTransfer` upload technique as every prior deploy, and hash-verified against `raw.githubusercontent.com` after commit (`app.js` `62df9ba0…`, `background.html` `be982aa2…`, `style.css` `3eda9355…`).

**Standing caveat, as always for anything popover/pointer-events related:** the empty-margin click-through can only be meaningfully judged against Owlbear's own real map-toggle button inside an actual room — worth the user's own quick check after deploying, same as every other popover-touching pass in this doc.

## Thirty-sixth pass: redesigned the icon again, and corrected a wrong assumption from the Twenty-fourth pass

The user asked to review the icon against the sibling `owlbear-grimoire` extension's icon and come up with a concept that reads immediately as a character sheet, rather than the Theme-card-plus-claw-marks design from the Twenty-fourth pass.

**A real finding, not just a style opinion.** `owlbear-grimoire`'s `icon.svg` carries a code comment stating that Owlbear's toolbar renders extension icons as flat white line art and ignores stroke/fill colors entirely — confirmed there against a live screenshot. Our icon had used `stroke="currentColor"` since the Twenty-fourth pass, on the assumption (recorded in that pass's own log entry above) that it would "inherit Owlbear's own toolbar tinting" — but that pass's verification was only ever a standalone SVG rendered against a mockup dark background and a parchment swatch, never checked inside real Owlbear. So that assumption was never actually true; it just happened not to matter as long as the mockup and the real toolbar treated color the same way, which they don't.

**Fix.** `icon.svg` now hardcodes `#f2f1f6` (grimoire's exact value) instead of `currentColor`, and its frame proportions (`rect` 22×24, `rx` 2.5, `stroke-width` 2.4) now match grimoire's too, for a consistent silhouette across the nebula-rum extension family — previously ours was `rect` 22×26 with `rx` 4 and a thinner `stroke-width` 2. Inside the frame: a simple head-and-shoulders person silhouette, sized to fill the frame rather than leaving empty space below. Chosen from several options shown to the user (a person with stat lines beneath, a name line over stat boxes, and a smaller person over a stat-box row) — the plain silhouette, enlarged, won out.

**Verification.** No fake-OBR-SDK stub needed here since nothing touches `app.js` — served `icon.svg` from the same local static server used for other passes' testing, rendered at 24px/32px/64px/128px against a dark swatch, confirmed it reads clearly as a person/character card even at real toolbar size with no line crowding. The actual toolbar tinting behavior (now hardcoded, not inherited) still can't be double-checked outside real Owlbear, same standing caveat as any popover-adjacent change in this doc.

## Installing extensions

In your existing room: open the **puzzle-piece icon** in the left toolbar → **Discover Extensions** (or paste a manifest URL directly if installing from a page above, or your own deployed Hero Sheet manifest URL) → Install. Extensions apply per-room, so if you run multiple Mist Engine games in separate rooms you'll install this stack once per room (or once if you keep everything in a single persistent room and just swap scenes per session).

## Configuring each piece for LitM

**Owl Trackers** — On a Hero or NPC token, open the tracker editor and add one tracker per active Stato, named exactly as you'd write it in-fiction (`stordito`, `convinto`, `mal-di-testa`), value = level. Delete the tracker when the Stato is removed, matching the "barra lo Stato" bookkeeping from the rules.

**Marked!** — Pre-build a label group for your table's common Stati (stordito, convinto, ferito, zoppicante, etc.) with a level suffix, and let players self-apply them during play for an at-a-glance view on the map — Owl Trackers stays the source of truth for the numeric level, Marked! is the visual flag.

**Bones!** — No special config; just make sure players know to roll `2d6` and add their computed Potere as a modifier (Potere can be zero or negative per the rules, so the modifier field should accept negative numbers).

**Mist Engine — Hero Sheet** — As GM, open the Settings tab once per campaign/room and set up your Theme categories (for LitM: rename the 3 pre-seeded ones to Origine/Avventura/Grandezza, or leave the English defaults if your table plays in English), and optionally repick the Tag/Status colors there too. Then open the Roster tab and add a character for each Hero at the table, assigning each to the right player (or "Everyone" for a one-shot's pregens). During play, use the Roster tab to check exact tag wording, Track progress, or Notes, or to edit a player's sheet directly (e.g. adding a Status, or toggling one of its 6 boxes) without interrupting them. The Compagnia tab holds the party's shared Company Theme — update its Mission/tags/tracks as the campaign evolves; any Hero can cross a Power tag when activating it. Use the expand button (top right) to pop the sheet open larger when you want to compare all of a Hero's Themes side by side.

**Journal!** — Use the Party tab for the running campaign log / Missioni in progress, and each player's Private tab for character-only secrets. The Narratore's own private notes work well for pre-rolled Oracolo results or Sfida twists you don't want visible yet.

**GM Vault** — Skip unless you re-host the PDFs somewhere with a public link; otherwise it's not worth the setup friction versus just keeping the PDF open in a second tab or window.

## Scene setup

LitM scenes are mostly theater-of-mind, so most maps can be a single evocative image with the grid turned off (Scene settings → Grid → None), rather than a tactical battlemap. Reserve an actual gridded map only for a Sfida where relative positioning genuinely matters (e.g., a chase or a siege) — Owlbear's default grid/token tools cover that case without any extra extension.
